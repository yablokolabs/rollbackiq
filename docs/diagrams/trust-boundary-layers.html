Trust boundary · RollbackIQ

Five registers between a recommendation and a running deployment

The agent's output is a proposal. Authority to change a deployment lives in the register below it, and each register can only act through the one underneath — which is why a green rollback job is not what certifies recovery.

Refusals

What the gate refuses

  • A missing, denied, expired or out-of-scope approval
  • An approver that is not a human identity
  • An environment that is not on the allowlist
  • A target this system never observed as healthy
  • Migration compatibility that is unknown rather than compatible
  • A replay of an idempotency key the ledger already consumed

Failure behaviour

How it fails

  • Fails closed: unknown means refuse, never "probably fine"
  • Reports every veto, not just the first one
  • deploy:regressed exits non-zero and writes no bundle unless the real detector fires
  • verify:recovery fails the pipeline when the window cannot prove stability
  • A rollback job that exited zero is never recorded as recovery

Source of truth

Where it lives

  • services/safety.py — the gate
  • models/incident.py — legal transitions
  • scripts/ci_rollback.py — gated executor and ledger
  • services/verifier.py — refuses to certify from reused data
  • duo/flows/…yaml — no deploy tool exists
